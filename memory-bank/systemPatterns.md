# System patterns

How the running system fits together. The rules for writing code live in `AGENTS.md` → *Conventions*; the file map lives in `readme.md` → *Project Structure*. This file records the runtime flow neither of those shows.

## Process and threads

- `main.main()` runs the `JarvisUI` (PyQt6) event loop on the main thread and `asyncio.run(JarvisLive.run())` in a daemon thread, started after the UI has an API key.
- `run()` loops forever: build `LiveConnectConfig` → `client.aio.live.connect(...)` inside an `asyncio.TaskGroup` → on a `_ReconnectSignal` or a dropped connection, rebuild. Voice change, audio-device change and server errors all reconnect through `request_reconnect(keep_context=...)`.
- Session resumption: the server's resumption handle is kept in RAM only (`_resume_handle`), never on disk, so a fresh launch starts a new conversation and the end-of-session summary still runs.
- Per-session transient state (vision, interrupt flags, tool-turn flags) is reset at the top of each connection in `run()`; new per-turn state belongs in that reset block.

## Audio path

- `_listen_audio`: the microphone callback (sounddevice thread) computes a level and pushes blocks to `out_queue` only when the mic is open (awake, not muted, push-to-talk held if enabled, not speaking).
- While asleep (wake-word mode) nothing is streamed: `_mic_asleep` numbers each block, keeps the last ~6 s in `_wake_ring` and feeds `core.wake_word.WakeWordDetector`, which runs the chosen engine (`core/wake_engines/`: openWakeWord, sherpa-onnx or Vosk) on its own thread. A detection reports the block where the phrase ended; `_wake_by_voice` (on the loop via `call_soon_threadsafe`) wakes up, and the first awake block sends the ring from just before that point, so a command said in the same breath reaches the model whole.
- Whenever the mic stops feeding the session — falling asleep, an answer finished while asleep, a connection made asleep — `_end_audio_stream` sends `audio_stream_end`; without it the server waits for audio and closes with 1008 "The operation was aborted".
- Falling asleep (`sleep()`) re-arms the detector: its model is reset and the mic is ignored for 3 s, because the assistant's own last words woke it. `_sleep_due` decides auto-sleep (idle timeout, or the short follow-up window) and never fires mid-answer or mid-tool; the `sleep_assistant` tool sleeps once the goodbye has played (`_on_answer_finished`).
- While the assistant speaks, mic blocks go to `core.barge_in.BargeIn` instead (opt-in "INTERRUPT" setting, mode "voice"). `BargeIn` uses `core.echo.EchoGuard` per block (plus its own residual floor and a settled-room requirement) and fires `_on_voice_barge_in` on the loop via `call_soon_threadsafe` after ~0.64 s of voice-like blocks in a short window.
- A voice barge-in only pauses: `_pause_for_barge_in` moves the queued answer into `_barge_hold`, and the playback loop flushes the device and puts its unplayed tail back in front. Transcribed words (`_has_words` on `input_transcription`), or a new reply after the server cut the old one, commit it through `interrupt()`; otherwise `_barge_check` resumes after 1.5–3 s and holds barge-in off for 6 s. The server's own `interrupted` does not settle a pause — its VAD fires on noise too — but it does stop the server generating, so on resume `_request_continuation` sends a text turn asking the model to finish from where it was cut; its reply queues behind the held audio. A server interruption within 3 s after a resume is treated the same way instead of discarding the resumed answer.
- Mode "name": while speaking, blocks go to the wake detector (`_mic_name_watch`) with EchoGuard's per-block verdict kept in `_wake_ring`; a detection interrupts (`_name_barge_in`) only if most blocks around the phrase were the user's voice, and the speech after the name is replayed like a voice wake.
- `_receive_audio` reads server messages: audio → `audio_in_queue`, transcripts → log and `core.viseme`, tool calls → `_execute_tool`, `interrupted` → interrupt bookkeeping.
- `_play_audio` writes PCM to the output device, reports each block to `EchoGuard.note_output`, and drives the avatar's mouth from `_pcm_level` / `_pcm_visemes`.
- `interrupt()` is the single interrupt path (UI button, "stop", a confirmed voice barge-in, interrupt-by-name): it drops queued and held audio, aborts the output stream, and discards the rest of the answer in flight.

## HUD

- `HudCanvas` steps its animation on a 16 ms timer and repaints at ~30 Hz while active, ~20 Hz idle, never while hidden. The centrepiece is `hud_style`: `face` (`core/avatar.py` HoloAvatar), `core` (reactor, `_paint_core`), `orb` (`core/orb_hud.py`) or `anime` (`core/anime_avatar.py`, a HoloAvatar subclass that only redraws). Each object is built once and kept, so the CONTROLS button cycles instantly and skips any style whose module failed to load (`can_show`). Renderers take colours as arguments and blend them opaquely onto `C.BG`.
- Colours: `class C` holds the live palette. `apply_ui_theme` sets the base (`neon` / `soft`), then `apply_ui_accent` shifts the hue-linked keys, keeping each base colour's saturation and value. A live switch rewrites every widget stylesheet in one regex pass (`retheme_all_widgets`); tints mixed with `_mix_hex` and `MetricBar` colours are rebuilt or looked up by key, because they are not palette hex strings.
- Fonts: every explicit font is `_font(size, weight)` — the per-OS `_MONO` face times `_UI_SCALE`, read once at import, so a TEXT SIZE change applies after a restart.
- Agent ring: `HudCanvas._poll_agent` reads `agents.job()` and `self_repair.state()` every ~0.5 s. A running job, or a self-repair from its first test run to its last, draws `_paint_agent`: a turning segmented ring and a comet in `AGENT_COLOURS[engine]` around the centrepiece's band, with the label and elapsed time at the top of the canvas. The end flashes a green or red ring for `AGENT_FLASH_S`. While either shows, the canvas repaints at the active rate.
- `ReplyCaption` (under the canvas) and `DesktopOrb` (parentless, always-on-top, click-through) both feed off what the HUD already has: the log lines on `_log_sig`, and the canvas's `speaking` / `muted` / `state` / `_amp_disp`. `DesktopOrb` steps only while it is wanted — the main window minimised or inactive, and its mode (`desktop_orb_mode`: off / speaking / always) asks for it now — and is woken by `_apply_state` and `changeEvent`; in "always" mode it idles at 20 fps.
- Compact mode: `MainWindow.enter_compact` hides the window (not minimises) and shows `CompactCard`, a parentless always-on-top tool window with its own `OrbHud`, a `ReplyCaption` subclass and buttons that call the window's handlers; `exit_compact` reverses it. The mode and the card's position are saved (`compact_mode`, `compact_pos`); `JarvisUI.__init__` re-enters the mode at startup. A confirm gate brings the HUD back (`_show_confirm_banner` calls `exit_compact`), compact mode is refused while one is pending, and the desktop orb stands down while the card is up. The window's ✕ still quits.
- `JarvisTray` (`QSystemTrayIcon`) refreshes its drawn icon and tooltip from `_apply_state` and the log lines. Quitting is explicit: `JarvisUI` turns off Qt's quit-on-last-window-closed (with the HUD hidden in compact mode, any other top-level window closing used to end the program silently); `MainWindow.closeEvent` (the ✕) and `quit_app` (card or tray) hide the card, prompt and tray icon and call `QApplication.quit()`. `[UI] Quitting — <reason>` is printed on every exit, including `shutdown_jarvis`.
- Quick prompt: `core.hotkey.GlobalHotkey` registers the key with `RegisterHotKey` on a thread with its own message loop and emits `_quick_prompt_sig`; when the key is taken, or off Windows, a `QShortcut` on the window and the card stands in. Typed text from the prompt and the HUD box goes through `submit_text`, which logs "You: …" on `_log_sig` and calls `on_text_command`; `JarvisLive._on_text_command` wakes a sleeping assistant before sending (typed text is never the room).

## Tool dispatch

`_execute_tool(fc)` first checks the arguments against the tool's declared schema (`core/tool_args.check`, schemas collected per config in `_tool_schemas`): harmless spellings are repaired, a missing required field, wrong kind or off-list enum returns `[ARGS_INVALID] Nothing ran: …` without running anything (after two in a row for one tool, the model is told to stop retrying). Then it routes by name: inline tools in `main.py` (`TOOL_DECLARATIONS`) → `ActionRegistry` (`actions/`) → `PluginRegistry` (`plugins/`). Action and plugin handlers run in the default executor, off the event loop. A handler returning nothing yields `action_loader.NO_RESULT` ("completion is unverified"), not "Done.". An action with `TOOL["snapshot"]` / `TOOL["verify"]` gets a verdict appended (see below). Results return as `FunctionResponse`; a tool's `scheduling` decides when a non-blocking result re-enters the conversation.

## Verification and computer use

- `ActionRegistry.run`: `snapshot(params)` → handler → unless the handler already failed (`health.failed` or a failure-worded result), `verify(params, result, before)` → `verify.tag` appends `[VERIFIED|UNVERIFIED|FAILED] detail` plus what to say. A FAILED verdict is a failed call in health (`no_effect`); results waiting for the user (`verify.WAITING`: [CONFIRM_SEND], [CONFIRMATION_PENDING]…) get none. `verify.poll` re-looks for up to `SETTLE_S` (1.2 s) before a verdict is final.
- Observations come from `core/desktop_state.py` (Windows): window list (via `_app_closer._win_list`), the foreground window, the UIA focused element and its value (`IUIAutomation.GetFocusedElement`, ~0.5 s with import), clickable UIA controls of a window (one `FindAll`), a browser's address bar (first Edit), and screen samples — a region reduced to a 48×64 grey grid; two "before" samples 0.55 s apart mask cells that change by themselves (caret, video).
- Actions with checks: `computer_control` (its `_snapshot` hovers the pointer first so a hover highlight is part of "before"; `screen_click` finds inside the handler and passes its own before/after through a thread-local), `computer_settings` (resolves the action like the handler; window actions on a named `value` bring that window forward first), `open_app`, `file_controller`, `browser_control` (the Playwright "before" is observed inside the handler after the session resumed its page; native navigation is checked through the address bar), `send_message`.
- Input: on Windows all typing is a clipboard paste (restored after 0.4 s); pyautogui's letter/digit key map is pinned to VK codes at import; a window is brought forward after a zero-length injected mouse move (not an Alt tap, which opens menus).
- `core/send_gate.py`: `ask(what, key, run, tool)` registers one pending send and a HUD CONFIRM (`confirm.request(key="send")`); `approve(key)` on the follow-up call needs the same key and `activity.user_answered_since(asked_at)`. Used by `computer_control.send_guard` (Enter / Ctrl+Enter in a chat message box that holds text — chat app process or a box named like "Message…"; Send buttons in `screen_click`) and `send_message action=send`.
- `send_message`: `open_conversation` brings the app forward, Esc, the jump shortcut (Slack/Discord Ctrl+K), pastes the name, waits up to 3 s for a UIA ListItem whose name before the comma equals it and clicks it, then requires the focused message box (or the title) to name the person. `draft` types into that box and remembers the window; `send` refocuses it and gates what is in the box now.
- `core/computer_use.py`: one run at a time on a daemon thread. Each round: `_look` (the named window, else the window in front, else the monitor of the window in front; a ≤1600 px JPEG plus numbered UIA controls), `_plan` (one VISION call, JSON with ≤3 actions), then actions — only click→type and type→press chain without a new look; a point-based click is skipped when 12 % of the region changed since the look; a point is confirmed by a close-look call. `_act` runs `computer_control`'s own snapshot / action / verify (keys directly, after the loop's own risk check) or `open_app`. `_risk`: Delete keys, Enter into a chat box, a click whose UIA label matches `_RISKY_RE`, or an action the model marked risky → `_ask_user` (announce + HUD CONFIRM, waits `ASK_TTL`; `proceed` needs the user's answer). `done` → `_final_check` yes / no / unknown. Ends on budgets, idle rounds, the user's mouse moving >30 px, pyautogui's fail-safe or `stop`; the outcome goes to `core/announce.py`. `HudCanvas._poll_agent` shows it as the `computer` ring.

## Health and self-repair

- Every call's outcome goes to `core/health.py`: the loaders record actions and plugins (an escaped exception = crash; `health.failed(why)` from the handler or a result starting like a failure = reported), `_execute_tool` records inline tools and refused arguments. Failures are written to `~/.jarvis/health/errors.jsonl` (redacted, an id per distinct error, the git version, the same id at most once a minute); the last 20 calls per tool, in RAM only, give ok / warn / bad. `health.install_hooks()` (in `main.main`) and `health.asyncio_handler` (on the session loop) journal uncaught thread and task exceptions.
- `core/capabilities.run_probes` checks the environment, every rejected action/plugin record and each tool's optional `TOOL["probe"]` concurrently (15 s cap), storing results in `~/.jarvis/health/probes.json`; `run_tests` runs pytest with a JUnit report in a temp folder and a scrubbed environment. `self_check` reads all of it.
- `core/self_repair.py`: `ask` (fingerprinted per task/error and base commit; refused if the user rejected it before or it failed twice) → `run` behind `activity.user_answered_since` → a pipeline thread: `git worktree add` on `self-repair/<id>` under `~/.jarvis/self_repair/wt/`, tests before, the agent through `agents.start_owned` (own system prompt, an `on_done` callback instead of the agent announcement), `git add -A` and `check_changes` on `diff --cached <base>` (protected paths, case-insensitive; no deletions, binaries, symlinks, mode changes, keys; only new `tests/test_*.py`), tests after (no new failures, no fewer tests), patch saved, announcement. The state persists in `current.json`, so a review survives a restart; a run cut off by one is marked failed.
- Review: `JarvisUI.show_review` → `ReviewOverlay` (diff, files, tests, report). APPLY calls `self_repair.apply` from the UI thread's worker: the diff hash and the checkout's HEAD must match, the worktree commits, the checkout fast-forwards, undo = `git reset --keep <base>`, `applied.json` records the pair. `revert_last` (the `undo` action) takes back the newest applied, not yet reverted change from `history.jsonl` while it is still HEAD — the in-memory undo stack does not survive the restart that loads a change. The `RepairPanel` under the AGENT panel shows health and state and has CHECK / START / ✕ (answer a waiting question; `run(by_button=True)` skips the spoken-answer gate) / REVIEW / RESTART / STOP.
- Restart: `restart_app` waits for the speech, saves the summary, `self_repair.spawn_restart` starts `core/restart_helper.py` (breakaway from the console's job when allowed) and the process exits. The helper waits for the old pid, starts the same command in a new console window on Windows (the old terminal does not show a process that outlived its parent), and watches 120 s: `started.ok` (written by `mark_started` on the first Live connect, which also clears `applied.json`) ends the watch; an error exit with HEAD still at the applied commit resets to its base, writes `rolled_back.json` (announced by the next instance via `startup_note`) and starts once more.

## Background results and coding

- `core/announce.py` queues results that arrive after the conversation moved on (a background command, a confirmed push, an agent's report, a relay event). `JarvisLive._run_announcer` sends them as one instruction when the session is connected, nobody is speaking, no answer or tool is open and the user has been quiet 4 s. Asleep, it still speaks (framed as `[NOTIFICATION]` news to pass on, not a request), `set_speaking(False)` restores SLEEPING and `_mic_asleep` keeps the wake detector deaf while the assistant talks. An item unsaid after 60 s goes to the tray (`announce.overdue` → `ui.notify`). A key replaces an older item still queued.
- `core/activity.py` records the assistant's speech ends (`set_speaking`) and user inputs (input transcription, typed text). `user_answered_since(t)` is the agent hand-off gate: a user input after the first speech end after `t`.
- The coding tools share `core/projects.py`'s current project (config `current_project`, `recent_projects`), found by a forgiving name in the usual code folders and every fixed drive's `Projects`.
- `run_command`: `core/shell_policy.classify` lexes the line (quotes respected, split at `| ; && || &`) and judges each piece by program and arguments → SAFE runs, CONFIRM goes to `core/confirm.py`, BLOCKED is refused. Commands run in PowerShell (pwsh when installed) as `core/jobs.py` jobs: a 10 s inline wait, then the job keeps running and its done-callback announces the result (a state flag under a lock decides between the inline reply and the announcement).
- `git_project` runs fixed git/gh argv; commit, branch and switch push undo entries; push and pr_create go through the confirm gate and announce their outcome. `project_workspace` records a sha256 per read and refuses an edit whose file changed since; edits and new files push undo entries. Files matching `projects.is_secret` are never read, searched, edited or committed.
- `core/agents.py` holds one agent job at a time. `ask` stores the task; `run` checks `activity.user_answered_since` and starts `claude -p --output-format stream-json` (permission mode `auto`, prompts `none`) or `codex exec --json --sandbox workspace-write` on a thread with API keys and Claude-session variables stripped and `JARVIS_AGENT_RUN=1` set. Events give steps, files, the session id (kept per engine and project for `follow_up`) and, for Claude, `rate_limit_event` usage. Codex models and limits come from `codex app-server` over stdio JSON-RPC (`model/list`, `account/rateLimits/read`). Settings and the last usage live in config `agents` (per-engine model and effort). `on_change` listeners drive the HUD's `AgentPanel`, the card's agent line and the tray menu.
- Agent-session relay: `core/agent_relay.install` adds `core/agent_hook.py` for `UserPromptSubmit`, `Stop` and `PermissionRequest` to `~/.claude/settings.json` and `~/.codex/hooks.json` (backup kept, only our entries touched). The hook drops JSON files into `~/.jarvis/agent_queue`; `JarvisLive._run_agent_relay` drains it every 2 s through `Relay.check` — turns shorter than `relay_min_turn_s` are skipped, permission prompts are held 15 s and dropped if the session transcript changed meanwhile — and queues announcements keyed per session.

## One-shot model calls

`core/gemini.py` runs a ladder: a throwaway Live session first (separate quota pool), then pinned REST models, then rolling `-latest` aliases. The VISION ladder (finding things on screenshots, computer use) is REST first with Live last, because coordinates read from a spoken transcription do not parse reliably. Failures cool a model down (429 → 5 min, 503/504 → 30 min, 404 → 6 h). The conversation's own Live model has exactly two rungs and steps only on quota or loss of access.

## Persistence

- `config/api_keys.json` (via `memory/config_manager.py`): key, identity, voice, colour, feature toggles, plugin settings, the current project, agent settings and last usage.
- `~/.jarvis/agent_queue/`: agent-session hook events, drained by the assistant.
- `~/.jarvis/logs/console.log` (previous run in `console.log.1`): a copy of stdout and stderr, installed by `main.main()` through `core/console_log.py`.
- `~/.jarvis/health/`: the error journal (`errors.jsonl`, rotated at 1 MB) and the last probe and test results (`probes.json`).
- `~/.jarvis/self_repair/`: worktrees (`wt/<id>`), per-run `patch.diff` / `diagnostics.txt`, `history.jsonl` (ready / applied / rejected / failed per fingerprint), `current.json`, and the restart watchdog's `applied.json`, `started.ok`, `rolled_back.json`.
- `memory/long_term.json` (via `memory/memory_manager.py`): long-term memory, session summaries, monitored topics. Only a ~900-character core block rides in the system prompt; the rest is fetched on demand by the `recall_memory` tool.
